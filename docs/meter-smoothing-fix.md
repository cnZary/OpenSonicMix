# 电平上升平滑修正

当前实现解决首版快攻电平的阶梯感，保留此前的待发电平合并与短峰值保留。窗口、布局、DPI、主题、设备协议与设置格式不变。

## 原因与修改

首版采用固定 2400 dB/s 上升。常见的 6 dB 变化只需 2.5 ms，在 60/144/240 Hz 下都于一帧内完成，随后等待约 87 ms 后的下一份设备数据。因此响应很快，但条体呈现“跳一下再停住”的阶梯。绘制裁剪本身使用浮点坐标，没有发现额外的整数电平量化。

上升现改为时间常数 20 ms 的指数追近，每帧根据剩余距离和实际经过时间推进，立即响应最新目标，不等待下一份输入，也不缓存一段数据后再播放。无论升幅大小，约 60 ms 完成 95% 的变化；目标改变时直接追踪新值，不继续播放旧动画。剩余误差小于 0.006 dB 时精确收敛，避免稳定电平无限请求帧。

另修正休眠后首帧固定使用 16 ms 的问题：改用从恢复订阅到首帧之间实际经过的单调时钟时间，后续帧继续使用 WPF 合成帧时间。144/240 Hz 下不会再无条件把几帧运动挤进首帧。

条体回落仍为 24 dB/s，峰值保持仍为 900 ms，峰值回落仍为 10 dB/s。仍使用现有逐帧渲染事件和位图/Visual 缓存，没有新增定时器。帧间短峰值、过期峰值处理、静音和稳定电平休眠均保留。

## 逐帧表现与延迟

6 dB 小幅上升后，在下一个 87 ms 输入到来之前，原算法在 60/144/240 Hz 下分别只有 1/5、1/12、1/20 帧发生条体移动；平滑算法可在这些中间帧持续推进。上升只在收到数据后开始；设备上报周期和真实声画同步未因算法调整而消失。

95% 响应时间与精确收敛时间是两个不同指标。指数曲线先完成主要变化，再渐近目标，不能把约 60 ms 写成已经精确到达满刻度。实际结果由基准工具同时输出这两个指标。

| 帧率 | 6 dB 上升期间运动帧数，旧→新（下次输入前） | 新版达到 95% | 新版 6 dB 精确收敛 | 新版空条至 0 dB 精确收敛 |
|---|---:|---:|---:|---:|
| 60 Hz | 1→5 | 66.67 ms | 150.00 ms | 200.00 ms |
| 144 Hz | 1→12 | 62.50 ms | 138.89 ms | 187.50 ms |
| 240 Hz | 1→20 | 62.50 ms | 141.67 ms | 187.50 ms |

这些是控件动画推进的测量，不是麦克风声音到屏幕的端到端延迟。新版用较长、逐渐减速的收尾换取连续运动，接受比首版单帧跳变更长的精确收敛时间。

## 验证与试用

Release 全量测试 **193 项通过，0 失败、0 跳过**，包括 Protocol/Shared/Tray 65 项、Panel 128 项。相较首版新增 13 项测试，覆盖 60/144/240 Hz 的小幅多帧上升、相同经过时间的帧划分一致性、95% 响应上限、稳定后精确收敛休眠、上升中收到较低目标，以及唤醒首帧的实际时间。原有回落、峰值保持、微秒/零时间步、短峰值与管道积压回归继续通过。

```powershell
dotnet test SonicCubePanel.slnx -c Release --no-restore
dotnet publish SonicCube.Tray/SonicCube.Tray.csproj -c Release --no-restore --self-contained false -p:PublishAot=false -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -o out/meter-smooth-fix
dotnet publish SonicCube.Panel/SonicCube.Panel.csproj -c Release --no-restore --self-contained false -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -o out/meter-smooth-fix
```

Panel 与 Tray 配套单文件发布均成功，输出目录为 `out/meter-smooth-fix/`。试用时退出旧面板和托盘程序，再运行此目录下的 `SonicCube.Panel.exe`。首版 `out/meter-response-fix/` 保留，便于人工对照。

## 性能测量范围

[基准工具](../tools/meter-response-benchmark/README.md) 使用五个真实 WPF 控件、预热后的静态缓存和实际保留 Visual 更新。除了原有变化输入，还纳入每 87 ms 小幅上升、保持与回落的阶梯场景，对比首版快攻与当前平滑实现。

平滑意味着在数据包之间更新更多中间帧，因此可能比单帧跳变增加少量计算和绘制工作，不能仅凭刷新频率不变就保证 CPU/GPU 占用相同。以下基准仅测托管推进/Visual 更新耗时及线程分配，不包含 GPU、WPF 合成器、实际帧率或端到端声画延迟。

2026-10-24，五个双声道电平表合计的每帧结果如下。每种输入/帧率预热 240 秒模拟帧，交错测量七轮，每轮 2400 秒模拟帧；耗时取中位数，括号为范围。双方相同的确定性时钟替换排除了墙钟读取开销。

| 输入 | 帧率 | 首版耗时 µs | 平滑版耗时 µs | 分配 B，首版→平滑版 |
|---|---:|---:|---:|---:|
| 混合变化 | 60 Hz | 2.829（2.769–2.889） | 3.630（3.452–3.713） | 336.12→452.62 |
| 混合变化 | 144 Hz | 2.691（2.584–2.824） | 3.516（3.373–3.736） | 317.29→448.60 |
| 混合变化 | 240 Hz | 2.563（2.548–2.612） | 3.417（3.351–3.613） | 311.87→447.41 |
| 上升阶梯 | 60 Hz | 2.159（2.102–2.311） | 2.659（2.572–2.728） | 269.18→333.17 |
| 上升阶梯 | 144 Hz | 2.054（2.017–2.116） | 2.600（2.553–2.659） | 246.24→317.24 |
| 上升阶梯 | 240 Hz | 1.996（1.975–2.033） | 2.538（2.528–2.713） | 239.68→312.85 |

本次测得托管耗时与分配均增加，不能沿用首版“分配下降 5–8%”的结论。五表合计每帧增加约 0.50–0.85 µs、64–136 B。按本基准最重的 240 Hz 混合输入换算，额外托管工作约 0.205 ms/秒，额外线程分配约 32.5 KB/秒；这不代表整程序或 GPU 的增加量。没有直接测量 GPU 占用。

九组相同电平/峰值状态的逐像素比较全部一致；既有 DPI 仅用于输出回归，本轮没有增加适配行为。原始结果保存在 `out/meter-smoothing-baseline/smoothing-results.json`，对应的首版源码在同目录的 `MeterBar.cs`。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/meter-response-benchmark/Run.ps1 -BaselineSourcePath out/meter-smoothing-baseline/MeterBar.cs
```
